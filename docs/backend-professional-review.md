# 后端专业度评审与重构路线（架构师视角）

> 评估对象：`ai-archmage` 独立 Express 后端（`server/*.ts`）+ 残留的 vite 中间件。
> 结论先行：当前后端"能跑、能用、单点安全漏洞已堵"，但本质是 **一个 Express 单文件 + JSON 文件存储的 Demo 级实现**。要称为专业，需要从数据持久化、分层架构、校验/错误处理、测试、可观测性、运维六个维度整体抬升，而不是继续在单文件里打补丁。

## 1. 当前最不专业的十点（按严重度分级）

### P0 — 生产前置，不修不能上公网

1. **持久化用 JSON 文件（根因）。** `store.ts` 是 read→modify→write，即使改成原子 rename，仍是**应用层竞态**：两个并发请求同读同写，后者覆盖前者 → 线索/配置静默丢失。无事务、无查询能力、无迁移、跨进程即崩。这是所有不专业的源头。
2. **"三套后端"并存。** vite dev 中间件 + vite preview 中间件 + 独立 server，**重复实现同一套 config/upload/leads**，已因此出过 401 bug。单一真相源缺失，改一处必漏。
3. **鉴权实质关闭。** `AUTH_ENABLED` 默认 false = 任何人知道 URL 即可改全站；开启时也只是明文比对 + 无刷新机制的 HMAC，无密码哈希、无审计日志。对商业站是硬伤。
4. **零自动化测试。** 处理"客户线索"这种直接关系收入的链路，却没有集成测试覆盖 leads / 校验 / 限流 / 上传，等于裸奔上线。

### P1 — 健壮性 / 一致性

5. **无分层。** `index.ts` 单体，路由、业务、数据访问全混，改一处要通读全文。
6. **校验散落手写**（`if (!contact)`），无边界 schema。缺 Zod 这类契约，无法生成 API 文档，422 语义不统一。
7. **错误模型不一致**（`{title,status,detail}` 与 `{error}` 混用），无统一错误中间件 / `asyncHandler`，抛错 = 未捕获 rejection = 挂起或裸 500。
8. **线索域不完整（业务核心却最弱）。** 无生命周期（新→已联系→成交/流失）、无去重、无服务端即时通知（客户提交你应立刻收到提醒）、无垃圾评分。

### P2 — Scale / 运维

9. **单进程无 cluster、无 Docker、上传落本地磁盘**（多实例/临时容器即丢）、body 30mb 过大、无 helmet/CSP、限流不回 `Retry-After`。
10. **配置无 schema 校验**（仅 fail-closed 查密钥）；无 OpenAPI 契约；无指标/追踪。

## 2. 目标专业架构（见附图）

- **单一后端服务**：删除 vite 中间件，dev 也走它（或反向代理）。消灭漂移源。
- **四层分层**：入口中间件 → 路由/中间件(auth/limit/validate) → 领域服务 → 仓储(接口化)。
- **数据**：SQLite(dev) / Postgres(prod) 经统一 Repository 接口；图片走对象存储。
- **横切**：启动配置 Zod 校验、统一错误模型、结构化日志+指标、全链路 request-id。

## 3. 落地路线

- **Phase A（上线前置）**：①删 vite 中间件、单一后端 ②SQLite + Repository ③Zod 边界校验 + 统一错误 ④真鉴权（argon2 + 会话/JWT + 审计日志）⑤helmet/CSP/`Retry-After` ⑥Vitest 集成测试 + Dockerfile + CI。
- **Phase B（业务稳健）**：⑦线索生命周期 + 去重 + 即时通知（邮件/Webhook）⑧GET 分页/筛选 + 指标 ⑨日志关联 ID 全量打通。
- **Phase C（规模，按需）**：⑩Postgres + 多实例 + 对象存储 + cluster。

## 4. 建议下一步

先落地 Phase A 的 **①~④**（消除根因），其余按排期。优先级最高的两刀是 **①删 vite 中间件统一后端** 与 **②SQLite + Repository**（直接根治竞态与漂移）。
